## Kontrakt mechanizmu i pliki projektu użytkownika

Nie tworzyć nowej bazy źródłowych wymagań. Model czyta aktualny zlecony obszar,
semantycznie ustala wpływ i proponuje mapę; pomocniki walidują referencje, kompletność
struktury, source hashes i bieżące wyniki. Nie klasyfikować naturalnego języka regexem.

Planowane artefakty (tworzone tylko podczas autoryzowanego użycia):

- `DOC_ROOT/work/<task-slug>/impact.json`: wyprowadzona mapa wymagania → fragmenty
  implementacji → ID configured checks, zależności i jawne gaps/rationale.
- `DOC_ROOT/work/<task-slug>/context.json`: ograniczone definicje sekwencyjnych zadań
  i pakiety kontekstu wyprowadzone z aktualnej mapy; źródła/autoryzacja/ograniczenia
  i check needs pozostają covered inputs. Bez transkryptu, sekretów i zrzutu repo.
- Istniejący `STATE.md`: Active Task wskazuje tę kolejkę i dokładny następny krok.
  Opcjonalna sekcja `## Execution Queue` przechowuje **wyłącznie administracyjny**
  checkpoint JSON (task IDs/statusy, próby, fingerprinty, run refs i blokadę). Cel,
  wymagania, before/after source data, parametry, limity, autoryzacja i cadence mają
  właściciela w covered context/spec, nigdy wyłącznie w wykluczonym STATE.

Te dwa JSON-y są objęte istniejącym fingerprintem `work/`, również gdy Git je ignoruje.
Nie dodawać nowego wykluczenia. Aktualizacja administracyjnego checkpointu STATE po
sprawdzeniu nie psuje ważnego wyniku; zmiana definicji zadania/kontekstu go unieważnia.
Nie dublować wyników runnera: checkpoint wskazuje faktyczny rekord i obserwację.
Zachować niepowiązane sekcje STATE, tolerować legacy brak queue; uszkodzona/zdublowana
sekcja lub niezgodny format jest diagnostyczny, nie pustą nową kolejką.

## P4-T2 — aktualna mapa wpływu

**Pliki:** nowe `gsr/lib/change-impact.js`, `gsr/docs/patterns/change-impact.md`,
syntetyczne fixtures pod `scripts/fixtures/phase-4/`, testy `scripts/test-autopilot.js`.

Proponowane API (nazwy można dopasować bez zmiany kontraktu):
- `prepareImpact(project, definition)` waliduje schemaVersion, unikalne IDs,
  requirement refs, implementation refs/check IDs/dependencies i zapisuje źródłowe
  fingerprinty; nie zgaduje semantyki ani nie nadaje verified/accepted.
- `inspectImpact(project, map)` zwraca current/stale/incomplete/diagnostic, zmienione
  lub brakujące źródła i obszary wymagające rozszerzenia inspekcji. Partial/gaps
  pozostają jawne; brak powiązania nigdy nie oznacza brak wpływu.

Mapa zawiera źródło celu/zmiany, zakres/wyłączenia, entries z requirement ID/ref,
implementation refs, check IDs, dependencies i podstawą powiązania. Wymaganie pod tym
samym ID ze zmienioną treścią unieważnia mapę. Source hashes służą do wykrywania zmiany,
nie dowodzą zależności/działania. Brakujące testy i nieznane powiązania rozszerzają
inspekcję oraz domyślną weryfikację. Nie generować zredukowanego profilu z samej mapy;
mapa wskazuje potrzeby, runner default nadal wykonuje wszystkie required (V1).

Walidować przez istniejący canonical project/reference: traversal, absolute paths,
symlink escape/dangling, brak pliku/sekcji i niejednoznaczność celu są diagnostyczne.
Czytać tylko jawne referencje; whole-project fingerprint wyłącznie gdy faktycznie
potrzebny do dowodu, nigdy do samego zbierania kontekstu. Zbyt duży plik wymaga
mniejszego fragmentu lub jawnego rozszerzenia, nie cichego obcięcia wymagań.

**Scenariusze:** P4-S1 zmiana bez konta dotyka wymogu, formularza, zapisu i checków;
P4-S2 unknown/missing mapping → gaps + rozszerzona inspekcja/default;
P4-S3 ten sam ID/inny tekst, zniknięcie implementacji lub external edit → stale;
P4-S4 niebezpieczne/niejednoznaczne refy i nieznane check IDs → diagnostic.

## P4-T3 — niewielki kontekst osobno dla kroku

**Pliki:** nowy `gsr/lib/task-package.js`, `gsr/templates/task-package-json.md`,
pattern wpływu/autopilota, testy i fixtures.

`preparePackage(project, map, task)` wymaga aktualnej mapy lub jawnie rozpoznanych
luk z planem rozszerzenia. Wynik: konkretne objective/doneWhen, wybrane requirement
fragmenty/kod, constraints/exclusions, decyzje wraz z owner/treścią, authorization
source/date, aktualna review cadence, dependencies, verification needs i refs do
istniejącego researchu/wyników. Początkowy zestaw odczytu ograniczony (preferuj <=6,
podobnie do stage packet); executor może rozszerzyć go z konkretnym powodem.

Nie gubić globalnych ograniczeń tylko dlatego, że krok ma wąski cel. Odmowa instalacji,
show-and-wait i późniejsze review-only wygrywają ze starym pakietem. Pakiet jest
nawigacją, nie nową autoryzacją. Sam hash nie nadaje researchowi aktualności semantycznej.
Odczyt odpowiednich fragmentów zamiast pełnej historii; nie dodawać skilli wyłącznie
po słowie kluczowym. Materialne zmiany źródeł/decisions wymagają odświeżenia.

**Scenariusze:** P4-S5 pakiet zawiera tylko związane źródła i wszystkie nadrzędne
ograniczenia/źródło/cadence; P4-S6 brak obowiązkowego kontekstu/za duży read set lub
changed source → diagnostic/expand, bez gotowego PASS; P4-S7 aktualny research reuse
z gaps/stale jawnymi. Dane osobiste poza task refs nie są czytane.

## P4-T4 — sekwencyjna kolejka, checkpoint i ograniczenie pętli

**Pliki:** nowy `gsr/lib/execution-queue.js`, wewnętrzny `gsr/scripts/autopilot.js`,
pattern `gsr/docs/patterns/autopilot.md`, integracja stage/task handoff.

CLI pozostaje wewnętrzny (nie dodawać publicznej komendy/flag): przygotowanie z
jawnego JSON wejścia, inspekcja, pakiet dla następnego zadania, record administracyjnego
wyniku oraz raport. Żadnego wykonywania shell strings/Markdown/modelu z JSON.
Model pracujący na hoście wykonuje kod i istniejący runner we własnych narzędziach.

Definicja kolejki ma unikalne zadania w kolejności zależności (odrzucić cykl/forward
nieuzgodnione dependencies/duplikaty) i odziedziczone granice. Jeden krok running
naraz. Checkpointy pending/running/checked/blocked; interrupted running wznawia się
po inspekcji, nigdy jako checked. Wczytywanie nie inicjuje pracy z SessionStart.

Przed start/resume: uzgodnić bieżący user operation/ograniczenia, package/map freshness,
zmiany plików i evidence. Zakończony krok nie jest bezwarunkowo skipowany: gdy jego
zależności lub źródła zmieniły się zewnętrznie, zwrócić reconciliation, zachowując
historyczny wykonany fragment i osobno nieaktualną weryfikację. Nie kasować postępu.
Current fingerprint nie jest samodzielnym dowodem semantycznej poprawności.

Zapis checked musi wskazywać bieżącą rzeczywistą passing obserwację runnera właściwego
projektu/profilu, z zachowaniem behavioral/manual limits i human acceptance osobno.
Nie czytać starego green, gdy najnowszy run failed/stale/interrupted. Przy zmianie
źródeł kontekstu po autoryzowanej edycji model odświeża mapę/pakiet semantycznie;
helper nie "przestemplowuje" ich automatycznie tylko dla PASS.

Próba przechowuje task ID, approach/strategy, actual input state i normalized result
(check statuses/exits/diagnostic, bez runId/timestamp jako pozornego postępu).
Powtórka bez zmiany wejścia/dowodu/postępu wymaga zmiany podejścia w zleceniu albo
konkretnej blokady. Nowy runId lub inne sformułowanie podsumowania nie zeruje licznika.
Zachować limit prób/kroków podany przez usera; bez niego zatrzymać identyczną drugą
bezproduktywną próbę, zamiast tworzyć niekończący się retry. Nie resetować limitu po
/clear. Zmiana strategii nie daje prawa do nieskończonej liczby kroków lub nowych kosztów.
Koszt/kredyty bez realnego pomiaru są unknown, nigdy twardym limitem w zł/USD.

Requested review boundaries i późniejsze narrowing zatrzymują affected execution,
nie niezależny read-only inspection. Kolejka/checkpoint nie interpretują naturalnej
mowy jako autoryzacji; model musi uzgodnić źródło i current operation. Nie dodawać
rutynowego potwierdzenia startu dla już autoryzowanej pracy.

**Scenariusze:** P4-S8 dwa kroki z rzeczywistym przerwaniem procesu pomocnika i
odczytem trwałego checkpointu w nowym procesie; P4-S9 external edit po checked →
reconciliation/stale, nie automatyczny skip; P4-S10 failed/unavailable/masked runner
wynik nie daje checked; P4-S11 dwie identyczne próby/nowe run IDs nie dają pętli;
P4-S12 późniejsze review-only i cadence blokują start zapisu produktu; P4-S13 malformed
checkpoint/missing queue refs nie tworzy nowej zielonej kolejki; P4-S14 limit prób/kroków
respektowany, koszt unknown. Test procesu to nie rzeczywisty reset sesji modelu.
