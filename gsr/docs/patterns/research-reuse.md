# Research selection, reuse and targeted refresh

Research serves a material decision, not a workflow checkbox. Start with the smallest
question that could change the next safe step. Routine copy corrections with no material
uncertainty need no broad competitor, marketplace or web sweep. Research and reading
existing records need no separate approval within an authorized task; host permissions,
installation, spending, account creation and product choices remain real boundaries.

## Read before researching

Use the current request/constraints and relevant feature/decision references first. Read
applicable existing findings, including legacy documents, before starting fresh research.
Optional new records live at `DOC_ROOT/research/<topic>.md` using
[the research record template](../../templates/research-record-md.md). Do not migrate the
whole research directory, duplicate a sufficient record or store secrets/raw transcripts.
Reference useful legacy findings directly and state applicability gaps. Quick/read-only
work needs no new research scaffolding merely to satisfy this pattern.

Judge each material claim against current requirement wording, constraints, stack/version,
use case, direct support and temporal sensitivity. Matching an unchanged requirement ID
alone is insufficient: changed wording under the same ID requires targeted review. If
readable support remains applicable/current, reuse it and record why; do not refresh only
because a document is old or automatically trust it because research once occurred.

## When refresh is needed

Refresh only the affected material question when relevant requirements/constraints change,
supporting source is missing/conflicting, temporal sensitivity makes the observation date
insufficient, or current uncertainty cannot safely rely on the finding. No universal TTL,
blanket "all research is stale" or "never repeat research" rule. Age is a signal, not proof
of failure. When applicability is uncertain, perform focused review rather than apply an
unrelated conclusion. Unreachable/missing/conflicting sources stay uncertain; distinguish
the original claim from current support and counterevidence instead of inventing certainty.

Record source publication/update where available, actual observed and reviewed dates,
applicable constraints, direct sources or observed artifacts, affected spec/decision refs,
counterevidence, remaining uncertainty and the reuse/refresh reason. Provenance is
`source`, `local observation` or `hypothesis`; model confidence/general knowledge without
verifiable support is a hypothesis. Saving or quoting it never promotes it to evidence.
A source claim is not automatically proven behavior in the project; a local observation
supports only its action/environment. Later automated verification remains separate.

## Bound the work and stop truthfully

Default to inline research. Delegate independent bounded questions only when useful,
supported and within the task/budget; each brief names the exact question, constraints,
existing findings and expected output. No unbounded agent sweep, paid API evaluation,
new tool install, account creation or broad D-pin experiment is implied.

Stop when evidence is sufficient for this question, a supplied budget is reached, or the
remainder needs human judgment/experiment. Record supplied budget, actual observed work
and stopping reason; unavailable time/cost stays unknown. A budget stop with unresolved
uncertainty is a partial finding, not research completion or proof. Continue independent
authorized work; ask only for the specific consequential decision or necessary boundary.

Preserve [deferred decisions](deferred-decisions.md): an existing D-pin does not mandate
fresh research or a question. Retain its recorded default/severity and revisit only when
new evidence makes a consequential choice actionable. Findings inform human choices,
never silently change prices/formats/scope or mark pins accepted.

## Carry the result across stages

Link relevant records/findings from the existing feature/plan or project-wide techstack
only where applicable; keep one current task summary and a minimal next-stage read set.
Preserve useful prior content and distinguish refreshed claims from unrechecked ones.
Research/spec/plan inputs remain covered by freshness; do not exclude records or move
requirements into administrative STATE to retain green. Stage handoffs still recommend
`/clear`, then **dalej**; the user resets and the next stage reads needed durable refs.

Reference/metadata checks validate documents only. Observed host/model behavior is
required to claim that agents actually reused/refreshed research or honored a budget.
